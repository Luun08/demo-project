# Security and privacy criteria for the existing-system comparison

**Owner:** Aknur — Security, Privacy & QA  
**Status:** Desk-review criteria, 22 October 2026

This sheet makes criteria C5, C6, C9 and C10 in [the existing-system comparison](existing-systems-comparison.md) explicit. It evaluates only what the cited public material documents. “Not established” must not be read as “the product does not have this control.”

| ID | Criterion | Evidence needed to mark “Yes” | Why it matters to this project |
|---|---|---|---|
| C5 | Role- or relationship-based access | Public documentation describes different permissions for caregiver, professional, proxy or account roles, and who can grant/revoke them. | A role alone is insufficient: child-specific relationship and assignment must also be checked. |
| C6 | Record-level visibility | Documentation says visibility can differ by individual note/record and identifies who can see each visibility level. | A family diary may contain entries intended only for assigned professionals. |
| C9 | Access revocation | Documentation explains how a caregiver/proxy/professional loses access and whether revocation affects already issued sessions. | Ended assignments must cease granting access promptly. |
| C10 | Audit/edit history | Documentation describes user-visible access history, edit history or a tamper-resistant audit trail and its scope. | Access to a child's records should be accountable and reviewable. |

## Evidence limits and update procedure

The current product table is a desk scan of selected public sources, not hands-on product testing or a security audit. For each new observation, record product/version, account/region, source URL, access date and exact feature evidence. If a source does not say, keep “Not established.” Do not infer implementation from marketing phrases such as “secure,” “private,” or “share.”

This comparison supports a design gap/question for user research; it does not prove market novelty or that the proposed platform is more secure.
