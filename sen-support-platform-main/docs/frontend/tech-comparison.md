# Сравнение технологий для фронтенда

## Контекст: какие требования влияют на выбор

По результатам опроса (`docs/research/evidence-to-requirements.md`) и требованиям (`ui-requirements.md`):
- основное устройство смартфон, поэтому mobile-first от 360 px;
- два языка интерфейса, kk и ru (FE-FR-11);
- три роли с разными экранами и правами, поэтому нужна строгая типизация данных и ролей;
- доступность WCAG 2.1 AA (FE-NFR-01);
- безопасность клиента: нет небезопасной вставки HTML, CSP, согласованное хранение токена (FE-NFR-06);
- небольшая команда и мало времени, поэтому важны скорость разработки и зрелая экосистема.

Условные обозначения: ✔ подходит, ~ частично, ✘ не подходит.

## 1. Библиотека интерфейса

| Критерий | React | Vue | Svelte |
|---|---|---|---|
| Опыт команды (работаем на React) | ✔ | ✘ | ✘ |
| Экосистема и готовые доступные компоненты | ✔ | ✔ | ~ |
| Типизация с TypeScript | ✔ | ✔ | ✔ |
| Скорость разработки в срок проекта | ✔ | ~ | ~ |
| Тестируемость | ✔ | ✔ | ✔ |

**Выбрано: React.** Решили срок и опыт команды, плюс зрелая экосистема. Vue и Svelte технически подошли бы, но их пришлось бы учить, а времени на это нет.
Документация: https://react.dev, https://vuejs.org, https://svelte.dev

## 2. Язык и сборка

| Критерий | TypeScript + Vite | JavaScript + Vite | Next.js |
|---|---|---|---|
| Надёжность типов для ролей и данных | ✔ | ✘ | ✔ |
| Скорость сборки и запуска | ✔ | ✔ | ~ |
| Нужен ли SSR | не нужен | не нужен | избыточен |
| Простота настройки | ✔ | ✔ | ~ |

**Выбрано: TypeScript + Vite.** Наш интерфейс это клиентское приложение за авторизацией, SSR и SEO не нужны, поэтому Next.js лишний. Типы защищают от ошибок в моделях ролей и видимости записей (Role, Visibility в `types.ts`).
Документация: https://vite.dev, https://www.typescriptlang.org, https://nextjs.org

## 3. Стили и компоненты

| Критерий | Tailwind CSS + собственные компоненты | MUI | Чистый CSS |
|---|---|---|---|
| Гибкость дизайна и контроль размеров (44 px, контраст) | ✔ | ~ | ✔ |
| Доступность готовых компонентов | ~ (делаем сами) | ✔ | ~ (делаем сами) |
| Размер и зависимости | ✔ | ~ | ✔ |
| Темы и крупные шрифты | ✔ (CSS-переменные) | ✔ | ✔ |

**Выбрано: CSS-переменные проекта плюс Tailwind CSS 4.** Дизайн-система проекта (палитра, размеры, состояния) задаётся переменными в `index.css`, Tailwind подключён для утилит. Доступность обеспечиваем сами: подписи полей, `aria-*` атрибуты, видимый фокус, цели ≥ 44 px; проверка Lighthouse. MUI отвергнут: заметно тяжелее и ограничивает собственный визуальный стиль.
Документация: https://tailwindcss.com, https://mui.com

## 4. Данные и состояние

| Критерий | React Context + fetch | TanStack Query | Redux Toolkit |
|---|---|---|---|
| Объём кода | ✔ | ✔ | ~ |
| Кэширование и ошибки запросов | ~ | ✔ | ~ |
| Подходит к текущему этапу (данные в памяти) | ✔ | ~ | ~ |
| Тестируемость | ✔ | ✔ | ✔ |

**Выбрано на этом этапе: React Context.** В прототипе данные локальные, внешних запросов ещё нет. При подключении backend планируем TanStack Query для запросов, кэша и состояний «загрузка / ошибка».
Документация: https://tanstack.com/query, https://redux-toolkit.js.org

## 5. Многоязычность (kk / ru)

| Критерий | Собственный типизированный словарь | react-i18next | Lingui |
|---|---|---|---|
| Простота | ✔ | ~ | ~ |
| Проверка наличия всех ключей на этапе сборки | ✔ (типы) | ~ | ✔ |
| Плюральные формы и форматирование | ~ | ✔ | ✔ |
| Размер и зависимости | ✔ | ~ | ~ |

**Выбрано на этом этапе: собственный словарь.** Словари kk, ru и en имеют общий тип в `i18n.ts`, пропущенный ключ даёт ошибку компиляции. Формы множественного числа пока не нужны. При росте числа текстов перейдём на react-i18next.
Документация: https://react.i18next.com, https://lingui.dev

## 7. Взаимодействие с backend

REST с описанием API в OpenAPI. GraphQL не нужен: сущностей немного, запросы типовые. Формат контракта согласуется с backend.
